## 背景

线上大量请求共享相同的开头：同一个系统提示词、同一段 few-shot 示例、多轮对话里的历史消息。每次都为这些前缀重新做预填充，是在重复劳动。**前缀缓存**把算过的 KV 块按内容登记起来，新请求如果以相同的 token 开头，就直接复用那些块，跳过对应的预填充。vLLM 的 Automatic Prefix Caching 和 SGLang 的 RadixAttention 都是这个思想。

## 核心概念

**键必须是整个前缀**：第 $i$ 个块（块大小 $P$）的键是

$$
\text{key}_i = \text{tokens}\bigl[0 : (i+1) P\bigr]
$$

而不仅仅是这一块自己的 $P$ 个 token。原因是一个 token 的 K、V 经过了注意力，依赖于它**前面所有** token。两个块内容相同、但前面的内容不同，它们的 KV 也不同，不能共享。

**只缓存满块**：最后一块没填满，之后还会追加新 token、改变内容，不能共享。

**遇到第一个不命中就停止复用**：块 $i$ 的 KV 只有在前面所有块都完全相同时才有效。

**块的三种状态**：

| 状态 | 引用计数 | 已登记 | 去向 |
| --- | --- | --- | --- |
| 使用中 | $> 0$ | 可能 | — |
| 可驱逐（缓存着但没人用） | $0$ | 是 | 再次命中时「复活」；空间不够时按 LRU 被驱逐 |
| 空闲 | $0$ | 否 | 直接分配 |

**分配新块的优先顺序**：

1. 空闲池中编号最小的块
2. 否则，驱逐**最早**变为可驱逐的块（LRU：最近最少使用），删除它的登记
3. 否则抛 `RuntimeError`

引用计数归零的已登记块不立即回收，留着等待以后的命中；真的缺空间时才驱逐最久没人用的那个。

## 用到的 Python 工具

- `tuple(tokens[:end])`：列表不可哈希，转成元组才能作字典的键。
- 两个字典：`键 → 块`、`块 → 键`，用于查找和驱逐时删除登记。
- `heapq` 最小堆管理空闲池；一个单调递增的计数器记录「变为可驱逐的时刻」。
- 向上取整：`-(-n // P)` 或 `math.ceil(n / P)`。

## 常见坑

- **只用块内容作键**：不同前缀后面的相同内容会被错误共享，测试专门检查。
- **共享了不满的最后一块**。
- **前面某块没命中，后面又去复用**：一旦不命中，之后所有块都要新分配。
- **复用一个可驱逐块时没有把它移出可驱逐集合**：它可能在使用中被驱逐。
- **驱逐顺序**：按变为可驱逐的先后，不是按块编号。同一次 `free_sequence` 释放的块，按它们在块表中的位置先后计时。
- **未登记的块归零后进了可驱逐集合**：它应直接回到空闲池。
- **同一个键登记两次**：键已登记给别的块时，新块保持未登记。

## 延伸

- **vLLM 与 SGLang 的实现差别**：vLLM 给每个满块算一个哈希，哈希里包含前一块的哈希，所以哈希代表整个前缀，思路和本题以整个前缀为键一致。SGLang 的 RadixAttention 把所有缓存过的序列组织成一棵基数树（radix tree），共同前缀对应共同的树路径，匹配最长前缀就是沿树往下走。
- **命中省的是什么**：命中的前缀不必再做预填充，节省的是计算，同时缩短首 token 延迟；显存上，多个请求共享同一批块，也省了空间。命中的前缀越长、重复的请求越多，收益越大。
- **哈希冲突**：真实系统里用哈希而不是完整的 token 元组做键，哈希冲突会让两个不同的前缀被错误地共享，所以要选抗冲突的哈希，或者在命中后再核对内容。本题直接用整个前缀的元组，没有这个问题。
- **LRU 的代价与替代**：LRU 实现简单，但对「偶尔出现的长前缀」不一定最优。基数树可以按叶子节点驱逐，保证被驱逐的块不会让别的缓存块失去前缀（失去中间的块，后面的块就无法再被命中）。
- **满块限制**：只有满块能被缓存，所以命中长度总是块大小的整数倍；块越大，粒度越粗，一个只差几个 token 的前缀可能整块都命不中。
- **和生成配合**：对话场景下，模型自己生成出的回答在下一轮会变成新的提示词的一部分，如果生成时填满的块也被登记，下一轮就能命中。
- **安全**：多个用户共享缓存时，命中与否会影响响应时间，理论上可以通过计时推测别人是否发过某个前缀。多租户部署通常要在缓存键里加入租户或隔离标识。

## 面试追问

1. **前缀缓存的键为什么不能只用块自己的 token？**
   KV 取决于该 token 前面的所有 token（注意力把前面的信息混了进来，位置编码也与绝对位置有关）。内容相同但前缀不同的块，KV 不同，不能共享。所以键要包含到该块末尾的整个前缀，实际中用「前一块的哈希 + 本块 token」滚动计算。
2. **为什么只缓存满块？**
   没填满的最后一块之后还会被追加 token，内容会变；而共享的块必须不再被修改。另外，只有满块才有稳定的、能作为键的内容。
3. **引用计数为 $0$ 的块为什么不立即回收？**
   它们保存着有可能被下一个请求命中的前缀。立即回收会让缓存毫无意义，因为请求通常先后到来、而不是同时运行。把它们放进可驱逐集合，真有需要时再回收，缓存的命中机会就保留到了最后一刻。
4. **缓存满了怎么办？为什么选 LRU？**
   先用空闲块，没有空闲块就驱逐最久没被使用的可驱逐块。LRU 利用了时间局部性：最近用过的前缀（如当前活跃的系统提示词、正在进行的对话）更可能再次出现。
5. **前缀缓存和 KV 块分配器的共享有什么区别？**
   块分配器里的共享发生在**同时在跑**的序列之间（并行采样、束搜索），用引用计数加写时复制管理。前缀缓存的共享发生在**先后到来**的请求之间，需要额外的「按内容查找」和「没人用时仍保留」，所以多了登记表和驱逐策略。
6. **哪些场景收益大？**
   请求之间有大段相同开头：长系统提示词、few-shot 示例、多轮对话的历史、对同一篇长文档反复提问。如果请求之间几乎没有共同前缀，则几乎没有收益。
