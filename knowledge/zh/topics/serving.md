## 解决什么问题

大模型上线后，要同时服务很多请求，每个请求都在逐 token 生成。有两件事决定了推理服务怎么搭：

- **解码很费显存、很吃带宽，不吃算力。** 每生成一个 token，要把所有层的权重和这个请求的全部历史 K、V 读一遍，却只做很少的计算。权重的读取可以让一批请求分摊，所以 batch 越大，每个 token 的成本越低。
- **batch 能开多大，由放得下多少 KV 缓存决定。** 显存里扣掉权重和激活，剩下的都用来放 KV：

$$
N_{\text{tok}} = \frac{M_{\text{GPU}} - M_{\text{权重}} - M_{\text{激活}}}{\text{每 token 的 KV 字节数}}
$$

$N_{\text{tok}}$ 是显存里同时能容纳的 token 总数（所有并发请求的上下文长度之和）。并发请求数大致是 $N_{\text{tok}}$ 除以平均上下文长度。所以整个专题可以看成在提高同一个数：**同样的显存里，同时服务多少个请求**。一套 vLLM 风格的服务按层次回答这个问题：

1. **缓存本身**（KV cache）：历史 K、V 不重算，存下来。
2. **缓存的存放方式**（分页）：不按最大长度整段预留，切成固定大小的块，按需分配。
3. **缓存的复用**（前缀缓存）：相同的开头只算一次、只存一份。
4. **请求的调度**（连续批处理）：每一步都重新决定谁跑，让显存和算力始终有活干。

## KV cache 有多大

每个 token 每层要存一份 K 和一份 V：

$$
\text{每 token 字节数} = 2 \cdot L \cdot H_{kv} \cdot d_h \cdot b
$$

$L$ 是层数，$H_{kv}$ 是 KV 头数，$d_h$ 是每头维度，$b$ 是每个元素的字节数，因子 $2$ 是 K 和 V。一个请求的缓存与上下文长度成正比，不是常数。

以 $32$ 层、$H_{kv} = 8$、$d_h = 128$、bf16（每元素 $2$ 字节）为例，每 token 是 $128$ KiB，$4096$ 个 token 的缓存就是 $512$ MiB。假设扣掉权重后有 $40$ GiB 留给 KV，那么一共能放约 $32$ 万个 token。

这个公式里的每一项都是可以下手的地方：GQA 减小 $H_{kv}$、MLA 换成低秩潜向量（这两条线的逐项对比见「注意力」专题），把缓存存成 8 bit 减小 $b$，滑动窗口限制参与缓存的 token 数。本专题关心的是另一半：缓存的尺寸给定后，怎么把它**管好**。

## 对比：显存怎么管，请求怎么调

先看存放方式。设每个请求的最大长度为 $S_{\max}$，实际长度为 $S$：

| | 连续预留 | 分页（块表） |
| --- | --- | --- |
| 分配单位 | 一整段 $S_{\max}$ | 固定大小的块，用到才分配 |
| 内部浪费 | 预留了但还没用到的 $S_{\max} - S$ | 只有最后一块没填满的部分 |
| 外部碎片 | 有，不同长度的段来去后留下空洞 | 无，块都一样大 |
| 共享 | 难，要整段拷贝 | 块级共享，引用计数 + 写时复制 |

再看调度方式：

| | 静态批处理 | 连续批处理 |
| --- | --- | --- |
| 调度粒度 | 一批（等最长的结束） | 一步（每生成一个 token 调度一次） |
| 结束的请求 | 空占位置到整批结束 | 立刻离开，位置让给等待者 |
| 新来的请求 | 等整批结束才能开始 | 下一步就能补进来 |
| 对 KV 管理的要求 | 低 | 高，请求长度不可预知、随时进出 |

后一行是两部分的连接点：连续批处理让请求随时进出，长度各不相同，连续预留会产生严重的碎片，所以现代推理引擎里两者总是一起出现。

## 显存碎片：连续预留为什么浪费

vLLM 的论文把传统做法的浪费分成三类：

- **预留浪费**：为将来要生成的 token 预留的位置，现在还没用上，但别人也不能用。
- **内部碎片**：按最大长度预留，请求结束时远没有用满。
- **外部碎片**：各请求的段大小不一，释放之后留下的空洞大小零散，总量够但拼不出一整段。

分页借用了操作系统虚拟内存的做法：逻辑上连续的序列，物理上散落在各个固定大小的块里，用一张表（页表 / 块表）做翻译。浪费的上界降到每个请求最后一块的 $P - 1$ 个 token。代价是多了一层间接寻址，注意力 kernel 要自己按块表去取数据（见「分页注意力」一题）。

## 前缀共享与写时复制

块级管理顺带带来了共享：

- **同一请求内部**：并行采样、束搜索的多个分支共享提示词的 KV。靠**引用计数**记录一个块有几个持有者，分支要往共享的块里写入新内容时，**写时复制**（CoW）：先给自己拷贝一份再写。
- **跨请求**：前缀缓存。块的键必须是**到这一块末尾的整个前缀**，因为一个 token 的 K、V 取决于它前面所有 token；只有前缀逐 token 相同，对应的块才能复用。引用计数降到 $0$ 的块不立即回收，留着等下一个请求命中，空间不够时再按 LRU 驱逐。

两者的区别在时间尺度上：CoW 管的是**同时在跑**的序列，前缀缓存管的是**先后到来**的请求。

## 调度：prefill、decode 与抢占

一个请求有两种性质完全不同的步骤：

| | prefill | decode |
| --- | --- | --- |
| 一步处理 | 整个提示词，几百到几万个 token | 1 个 token |
| 瓶颈 | 算力（大矩阵乘） | 显存带宽（读权重和 KV） |
| 影响的指标 | TTFT | TPOT / ITL |

把两者混在一个 batch 里，一个长提示词的 prefill 会让同批所有 decode 请求在这一步等很久，用户看到的是生成中途卡顿。常见的缓解思路有两种：

- **chunked prefill**：把长提示词切成块，每步只做一块，与 decode 请求共用一步的 token 预算。预算先分给各个 decode 请求（每个 $1$ 个），剩下的才给 prefill。连续批处理一题的预算约束就是这个思路的简化版，只是它不切块，提示词必须整个放进预算。
- **PD 分离**（prefill-decode disaggregation）：把两个阶段放到不同的实例甚至不同的机器上，各自按自己的瓶颈配置并行方式和 batch 大小，互不干扰。代价是 prefill 完成后要把 KV 缓存传给 decode 实例，这部分网络传输是新增的开销。

另一个问题是显存不够。每个请求生成时都会不断长出新 token，需要新块；如果空闲块用完了，调度器只能**抢占**（preempt）某个正在运行的请求，把它的块让出来：

- **swap**：把它的块拷贝到 CPU 内存，等有空间了再拷回来。省了重算，但占用 PCIe 带宽。
- **recompute**：直接丢掉它的 KV，之后当作一个新请求重新做 prefill（已经生成的 token 也算进提示词里）。实现简单，如果开了前缀缓存，丢掉的块有可能还没被驱逐，重算的实际代价会小一些。

## 指标

| 指标 | 含义 |
| --- | --- |
| TTFT | 首 token 延迟 = 排队时间 + prefill 时间 |
| TPOT | 平均每个输出 token 的时间 = (总延迟 − TTFT) / (输出 token 数 − 1) |
| ITL | 相邻两个 token 的实际间隔，可以看尾部（卡顿） |
| 吞吐 | 单位时间内所有请求生成的 token 总数 |

吞吐和延迟互相牵制：batch 开得越大，每个 token 的成本越低、吞吐越高，但每一步更慢，单个请求的 TPOT 变大。服务的目标通常写成「在满足 TTFT 和 TPOT 上限的前提下，吞吐尽可能大」。

## 演进

1. **KV cache**：自回归解码的标准做法，把历史 K、V 存下来，每步只算新 token。
2. **迭代级调度（Orca，2022）**：调度粒度从一批变成一步，解决了静态批处理的空转和排队。
3. **PagedAttention（vLLM，2023）**：借用虚拟内存的分页思想管理 KV，把显存浪费降到很低，让连续批处理能真正开大 batch。
4. **前缀缓存**：vLLM 的 Automatic Prefix Caching 用块哈希，SGLang 的 RadixAttention 用基数树（radix tree），思想一致：按内容登记 KV，跨请求复用。
5. **chunked prefill 与 PD 分离**：处理 prefill 与 decode 之间的干扰，前者在同一批里切块混合调度（例如 Sarathi 系列工作），后者把两个阶段分到不同的资源上（例如 DistServe、Splitwise）。

## 怎么选

- **单请求、低并发**：普通 KV cache 就够了，分页和连续批处理的收益体现在高并发上。
- **高并发在线服务**：连续批处理 + 分页 KV 是基本配置。
- **大量请求共享开头**（系统提示词、few-shot 示例、多轮对话、同一文档上的多次提问）：打开前缀缓存，命中的部分跳过 prefill，TTFT 明显下降。几乎没有共享时，前缀缓存没什么收益，也基本没有损失。
- **长提示词让生成卡顿**：用 chunked prefill 控制每步的 token 预算。
- **规模大、对 TTFT 和 TPOT 的上限要求都严**：考虑 PD 分离，代价是系统复杂度和 KV 传输。
- **显存紧张**：优先看模型本身的 KV 压缩（GQA、MLA），其次是把缓存量化到更低的位宽。

## 题目顺序

1. **KV Cache 注意力**：先搞清楚缓存的是什么、为什么增量解码和完整前向必须一致，以及带偏移的因果掩码。
2. **KV Cache 块分配器**：把缓存从「一整段张量」换成「固定大小的物理块」，学引用计数和写时复制。
3. **分页注意力**：通过块表把分散的页取出来做注意力，对应前一题管理的那些块。
4. **前缀缓存**：在块分配器上加按内容登记、可驱逐状态和 LRU，看清楚为什么键是整个前缀。
5. **连续批处理调度器**：最后一层，在每一步的 token 预算和序列数限制下，决定谁进谁出。

## 面试追问

1. **KV cache 有多大？怎么估算？有哪些办法压缩？**
   每 token 是 $2 L H_{kv} d_h b$ 字节，总量与并发请求数、各自的上下文长度成正比。压缩的方向：减少 KV 头（MQA、GQA）、低秩压缩（MLA）、存成更低位宽、滑动窗口只保留最近的 token，以及用分页减少浪费。
2. **连续预留 KV 缓存有什么问题？分页怎么解决？**
   按最大长度预留，实际用不满就是内部浪费；不同大小的段来去，还会产生外部碎片。分页把缓存切成固定大小的块，按需分配，每个请求最多浪费最后一块的一部分，也没有外部碎片。代价是间接寻址：注意力 kernel 要按块表取数据。
3. **解码为什么是访存受限？为什么 batch 大了吞吐就高？**
   解码每步只处理一个新 token，计算量很小，却要把权重和 KV 缓存读一遍。权重对所有请求是共享的，一批请求只读一次，所以每个 token 摊到的权重读取随 batch 增大而下降；而 KV 是每个请求自己的，不能共享，是 batch 变大后越来越主要的代价（见「性能估算」专题的推理 roofline）。
4. **连续批处理和静态批处理有什么区别？为什么它能同时提升吞吐和延迟？**
   静态批处理等整批最长的请求结束；连续批处理每一步都重新调度，结束的请求立刻离开，等待的请求立刻补入。GPU 上不再有短请求陪跑造成的空转，新请求也不必等整批结束，所以吞吐更高、排队延迟更低。
5. **为什么前缀缓存的键要用整个前缀，而不是块自己的内容？**
   一个 token 的 K、V 经过了注意力，取决于它前面所有 token（位置编码也取决于绝对位置）。两个块内容相同但前缀不同，它们的 KV 也不同，不能共享。
6. **prefill 和 decode 混在一起会出什么问题？怎么缓解？**
   prefill 一步处理很多 token，会让同批的 decode 请求在这一步等很久，ITL 出现尖峰。可以用 chunked prefill 把长提示词切成块，与 decode 共用每步的 token 预算；规模更大时用 PD 分离，让两个阶段互不干扰。
7. **显存不够用了，调度器怎么办？**
   抢占某些请求，把块让出来。swap 是把块搬到 CPU 内存，之后搬回；recompute 是丢掉 KV，之后重新做 prefill。前者占用 PCIe 带宽，后者占用算力，实现上 recompute 更简单。
8. **TTFT 和 TPOT 分别由什么决定？**
   TTFT 是排队时间加 prefill 时间，主要受提示词长度、前缀缓存命中和调度策略影响；TPOT 是每步 decode 的耗时，主要受 batch 大小、KV 缓存长度和同批是否混入 prefill 影响。
