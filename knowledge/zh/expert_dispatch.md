## 背景

混合专家（MoE）层里，路由器为每个 token 选 top-k 个专家。在**专家并行**中，不同专家放在不同的卡上，token 要通过 all-to-all 发到对应专家所在的卡，算完再发回来。

为了让通信缓冲区和专家计算的形状**固定**（方便高效实现），每个专家只预留 $C$ 个槽位，即**专家容量**。路由不均衡时，热门专家的槽位会被占满，多出的分配直接**丢弃**（这些 token 在这个专家上的贡献为 $0$，它们仍然可以通过残差连接往下传）。GShard、Switch Transformer 都这样做。

## 核心公式

**门控**：$p = \operatorname{softmax}(\text{router\_logits})$，取每个 token 概率最大的 $k$ 个专家 $e_{n,0}, \dots, e_{n,k-1}$（按概率从大到小），在这 $k$ 个之间重新归一化：

$$
g_{n,r} = \frac{p_{n,\, e_{n,r}}}{\sum_{r'=0}^{k-1} p_{n,\, e_{n,r'}}}
$$

**容量**：总分配数是 $N k$，平均每个专家 $Nk/E$ 个，再乘一个余量系数（如 $1.25$）并**向上**取整：

$$
C = \left\lceil \frac{\text{capacity\_factor} \cdot N \cdot k}{E} \right\rceil
$$

系数越大，丢弃越少，但空槽位（浪费的计算和通信）越多。

**分配优先级**：先按 token 顺序处理所有 token 的**第一选择**，再处理所有第二选择……这样每个 token 最想去的专家优先得到满足，不会因为排在后面就被别人的次选挤掉。

**输出**：

$$
y_n = \sum_{r\,:\,(n, r) \text{ 被接收}} g_{n,r} \cdot \operatorname{Expert}_{e_{n,r}}(x_n)
$$

被丢弃的分配贡献为 $0$，剩下的门控权重**不再**重新归一化。

## 形状

| 量 | 形状 |
| --- | --- |
| `x`、输出 | `(N, D)` |
| `router_logits`、$p$ | `(N, E)` |
| top-k 的概率、下标、门控 | `(N, k)` |
| 专家 $e$ 的输入 | `(n_e, D)`，$n_e \le C$ |

## 用到的 PyTorch 操作

- `probs.topk(k, dim=-1)`：返回按从大到小排序的值和下标。
- 用整数下标列表索引：`x[tokens]`，把分给某个专家的 token 堆叠起来，一次调用专家。
- `out.index_add(0, tokens, src)`：把 `src` 的各行加到 `out` 的指定行上（同一行可以被加多次）。它返回新张量，不会原地修改。
- `math.ceil`。

## 常见坑

- **容量向下取整**：要用 $\lceil \cdot \rceil$。
- **按 token 优先而不是按选择序号优先**：先处理完 token 0 的两个选择再处理 token 1，会让 token 0 的次选挤掉 token 1 的首选。
- **丢弃后重新归一化门控**：本题要求不重新归一化。
- **每个 token 单独调用专家**：结果对，但慢，且测试要求每个专家只调用一次、按接收顺序堆叠行。
- **门控断开了梯度**：比如用 `.item()` 取出门控值再参与计算，梯度就传不回 `router_logits`。
- 不要原地修改输入。

## 延伸

- **专家并行里的 all-to-all**：每个 MoE 层前向有两次：分发（把 token 送到专家所在的卡）和合并（把专家输出送回）；反向再各一次，共 $4$ 次。因为每个专家的缓冲区固定为 $C$ 个槽位，每卡发出的缓冲区大小固定为

$$
E \cdot C \cdot D = \text{capacity\_factor}\cdot N k \cdot D
$$

  个元素（$N$ 为本卡的 token 数），其中约 $\frac{P-1}{P}$ 要发往别的卡。例如 $N=8192$、$k=2$、$E=64$、$D=4096$、容量系数 $1.25$：$C = 320$，缓冲区共 $20480$ 个槽位，bf16 下约 $168$ MB，而实际有用的只有 $N k = 16384$ 个槽位（约 $134$ MB）；容量系数越大，空槽位越多，浪费的通信和计算也越多。
- **容量的另一个作用是限制最坏情形**：没有容量时，一个热门专家可能收到远超平均的 token，它所在的卡成为落后者，整个步的时间由最慢的卡决定。有容量限制，每个专家的计算量有上界，代价是丢掉一部分分配。
- **丢弃的是「分配」而不是 token**：token 的某个选择被丢掉，只是少了这一个专家的贡献，它仍通过残差连接往下传，另一个选择如果被接收，输出照常加上。配合负载均衡损失（见「模型架构」专题的 MoE 负载均衡一题）可以让路由更均匀，丢弃更少。
- **不丢 token 的做法**：dropless 实现不设容量，让每个专家处理可变数量的 token，MegaBlocks 用块稀疏矩阵乘解决变长带来的形状问题。代价是形状变动，通信量也不再固定。
- **梯度怎么到达路由器**：top-k 的选择本身不可导，路由器的梯度来自输出里乘的门控权重 $g$。被丢弃的分配没有梯度。
- **专家怎么算**：每个专家把分给它的 token 堆成一个矩阵，一次矩阵乘完成。实际系统里不会逐专家循环，而是把各专家的矩阵乘合成一次 grouped GEMM。
- **和专家内部的张量并行不同**：EP 保持每个专家的矩阵完整，代价是 token 要在卡之间路由；把每个专家的矩阵也切开则是 TP，通信变成层内的 all-reduce。两者可以叠加。

## 面试追问

1. **为什么要给每个专家设容量？**
   为了形状固定：通信缓冲区和专家的矩阵乘形状都是常数，方便高效实现；同时限制热门专家的负载，避免该卡成为拖慢全局的落后者。代价是路由不均衡时要丢弃一部分分配。
2. **容量系数怎么选？**
   在丢弃率和浪费之间折中。系数大，丢弃少，但空槽位多，浪费通信和计算；系数小则相反。比如本题默认的 $1.25$，即略高于平均，同时配合负载均衡损失让路由更均匀。
3. **专家并行每层有几次通信？量级是多少？**
   前向 $2$ 次（分发、合并）all-to-all，反向 $2$ 次，共 $4$ 次。每次每卡的量约为 $\text{capacity\_factor}\cdot N k D\cdot\frac{P-1}{P}$，与 token 数和 top-k 成正比。top-k 越大（例如细粒度专家）通信越重，这也是 EP 倾向放在机内的原因。
4. **被丢弃的 token 会怎样？训练和推理的处理一样吗？**
   丢弃的是 (token, 专家) 这个分配，该专家的贡献为 $0$，token 仍通过残差往下传。丢得多会伤害训练效果；推理时丢 token 会直接影响输出，实践里可以放宽容量或使用不丢 token 的实现。
5. **为什么分配时要「所有 token 的第一选择先于第二选择」？**
   这样每个 token 最想去的专家优先得到槽位，次选不会因为 token 排在前面就挤掉别的 token 的首选。按 token 顺序逐个处理则会让靠前 token 的次选占掉后面 token 的首选槽位。
