## 背景

想让模型更强通常要增加参数，但参数越多、每个 token 的计算量也越大。**混合专家**（Mixture of Experts，MoE）打破了这个绑定：把一个 FFN 换成 $E$ 个并列的「专家」FFN，再加一个**路由器**，每个 token 只送给其中 $k$ 个专家（通常 $k = 1$ 或 $2$）。

- 总参数量 ≈ $E$ 个 FFN
- 每个 token 的计算量 ≈ $k$ 个 FFN

Mixtral 8×7B 共有约 47B 参数，但每个 token 只激活约 13B。DeepSeek-V3、Qwen-MoE 等模型都使用 MoE。

## 核心公式

**路由**：路由器是一个线性层，为每个专家打分：

$$
\ell = x\, W_r \in \mathbb{R}^{E}
$$

选出得分最高的 $k$ 个专家 $\mathcal{T} = \operatorname{topk}(\ell)$，只在这 $k$ 个分数上做 softmax 得到门控权重：

$$
g_i = \frac{e^{\ell_i}}{\sum_{j \in \mathcal{T}} e^{\ell_j}},\qquad i \in \mathcal{T}
$$

这和「先对全部 $E$ 个分数做 softmax，再把选中的 $k$ 个概率重新归一化」的结果完全一样，因为分母中的公共因子会约掉。

**输出**：被选中专家输出的加权和：

$$
y = \sum_{i \in \mathcal{T}} g_i \cdot \operatorname{Expert}_i(x),
\qquad
\operatorname{Expert}_i(x) = W_2^{(i)}\, \operatorname{ReLU}\bigl(W_1^{(i)} x + b_1^{(i)}\bigr) + b_2^{(i)}
$$

## 形状

| 量 | 形状 |
| --- | --- |
| `x` | `(B, S, d_model)`，展平为 `(B·S, d_model)` 个 token |
| 路由分数 | `(B·S, E)` |
| top-k 的分数、下标、门控 | `(B·S, k)` |
| 输出 | `(B, S, d_model)` |

## 实现思路

逐个 token 调用专家太慢。更好的做法是**按专家分组**：对每个专家 $e$，找出所有选中它的 token（布尔掩码），把它们堆在一起一次送进专家，再把结果乘以对应的门控、加回这些 token 的输出位置。

## 用到的 PyTorch 操作

- `nn.ModuleList([...])`：存放多个专家，子模块才会被注册（普通 Python 列表不会）。
- `logits.topk(k, dim=-1)`、`torch.softmax(vals, dim=-1)`。
- 布尔掩码 `mask = top_idx[:, j] == e`，`x[mask]` 取出这些 token。
- `x.reshape(-1, D)` 展平，最后 `reshape` 回原形状。

## 常见坑

- **对全部专家做 softmax 后直接取 top-k 概率**：没有重新归一化，权重之和小于 $1$，与本题要求不同。
- **用 Python 列表存专家**：参数不会被注册，优化器找不到，测试也会检查 `self.experts`。
- **没有展平 batch 和序列维**：路由是逐 token 的。
- **门控形状不匹配**：`(n, 1)` 的门控才能和 `(n, d_model)` 的专家输出广播相乘。

## 延伸

- **总参数与激活参数**：只算 FFN 部分，总参数是 $E \cdot P_{\text{ffn}}$，每个 token 实际用到的是 $k \cdot P_{\text{ffn}}$。注意力、嵌入等共享部分每个 token 都要用，所以整个模型的激活参数比例没那么小。Mixtral 8×7B 是 $E = 8$、$k = 2$，总参数约 47B，激活约 13B。
- **显存与计算不对称**：算力只看激活参数，显存却要放下**所有**专家。解码时 batch 里的 token 分散到不同专家，一步下来几乎所有专家权重都要读一遍，速度受限于带宽而不是算力（见「性能估算」专题）。所以 MoE 的收益主要在训练和大 batch 吞吐上。
- **top-1 时的梯度问题**：$k = 1$ 时，在单个分数上做 softmax 恒等于 $1$，门控对路由器没有梯度，路由器学不到东西。Switch Transformer 的做法是用对全部专家 softmax 之后的原始概率当门控，不重新归一化。本题测试里 $k = 1$ 只是用来固定路由、验证专家计算，不要把它当成训练设定。
- **共享专家与细粒度专家**：DeepSeekMoE 把专家切得更小、数量更多，并保留一部分**共享专家**，所有 token 都经过它，负责通用知识，路由专家就可以更专注。DeepSeek-V3 每层有 1 个共享专家和 256 个路由专家，每个 token 选 8 个路由专家。
- **门控函数的变体**：Mixtral 与本题一样，对选中的 top-$k$ 个分数做 softmax；DeepSeek-V3 先用 sigmoid 给每个专家打分，再对选中的专家归一化。
- **专家的结构**：本题的专家是 Linear-ReLU-Linear，实际的大模型里专家通常是 SwiGLU 的 FFN。
- **实现与通信**：本题按专家循环，专家多了会很慢。工程上先按专家把 token 排序，再用 grouped GEMM（一次调用算完大小不一的多个矩阵乘），或者像 MegaBlocks 那样用块稀疏的方式，避免丢 token。多卡时把专家分到不同卡上（专家并行），token 要通过 all-to-all 发给对应专家，这部分见「分布式训练」专题的专家分发一题。
- **负载均衡**：见「MoE 负载均衡损失」一题。

## 面试追问

1. **MoE 为什么能在相同计算量下更强？**
   参数量决定模型能存多少知识，计算量取决于每个 token 激活多少参数。MoE 把两者解耦：总参数多，每个 token 只用其中一小部分，所以同样的算力能训出容量更大的模型。
2. **MoE 推理时省显存吗？**
   不省。所有专家都要常驻显存，只是每个 token 少算了。batch 小的时候还会因为各 token 选的专家不同，几乎读遍所有专家权重，带宽压力不比稠密模型小。
3. **top-$k$ 之后做 softmax，和先全局 softmax 再对选中的归一化，结果一样吗？**
   一样。全局 softmax 的分母对所有专家相同，选中之后重新归一化时会约掉。
4. **$k = 1$ 时重新归一化会有什么问题？**
   门控恒为 $1$，路由器得不到任务损失的梯度。Switch Transformer 用的是不重新归一化的原始概率。
5. **共享专家有什么用？**
   给所有 token 提供一条稠密通路，承载通用知识，减少路由专家之间的冗余，路由专家可以更专门化。
6. **为什么 MoE 需要负载均衡？**
   路由器容易越练越偏，少数专家过载，多数专家闲置，等于白白浪费参数；专家并行时还会让个别 GPU 成为瓶颈。
