## 背景

早期推理系统给每个请求按**最大长度**预留一段连续的 KV 缓存，但大多数请求生成不到最大长度，显存大量浪费；不同长度的请求来来去去，还会留下碎片。vLLM 借鉴操作系统的**分页**：把 KV 缓存切成固定大小的**物理块**，按需分配，用一张表记录每个序列用了哪些块。每个序列最多浪费最后一块里没填满的部分。

块还可以在序列之间**共享**：

- **并行采样**：一个提示生成多个回答，提示部分的 KV 完全相同
- **束搜索**：多条候选共享相同的前缀

共享靠**引用计数**管理；某个序列要往共享块里写新内容时，先复制一份再写，即**写时复制**（copy-on-write，CoW）。

## 核心概念

**引用计数**：块 $b$ 的引用计数 $\text{ref}(b)$ = 当前持有它的序列数。不变式：

$$
\text{块 } b \text{ 空闲} \iff \text{ref}(b) = 0 \iff b \in \text{空闲池}
$$

| 操作 | 效果 |
| --- | --- |
| `allocate()` | 取最小的空闲块，$\text{ref} \leftarrow 1$ |
| `fork(b)` | 又一个序列共享 $b$：$\text{ref}(b) \mathrel{+}= 1$ |
| `free(b)` | 一个持有者放弃 $b$：$\text{ref}(b) \mathrel{-}= 1$，减到 $0$ 时回到空闲池 |
| `copy_on_write(b)` | 见下 |

**写时复制**：

- $\text{ref}(b) = 1$：只有自己在用，直接写，返回 $b$
- $\text{ref}(b) > 1$：分配一个新块 $b'$，自己改用 $b'$；$b$ 少了一个持有者，$\text{ref}(b) \mathrel{-}= 1$，返回 $b'$

**最小堆**：要求每次分配「当前最小的空闲编号」。最小堆支持 $O(\log n)$ 的插入和取最小值，比每次排序或线性扫描都快。`list(range(n))` 本身已经满足堆的性质，可以直接用。

## 用到的 Python 工具

- `heapq.heappop(h)`、`heapq.heappush(h, x)`：最小堆。
- 一个列表 `refs = [0] * n` 存引用计数。
- `raise RuntimeError(...)`、`raise ValueError(...)`。

## 常见坑

- **写时复制失败时状态被改了**：如果没有空闲块，要在修改任何引用计数**之前**抛异常。先分配，成功后再给旧块减引用。
- **重复释放没有报错**：对引用计数为 $0$ 的块做 `free`、`fork`、`copy_on_write` 都要抛 `ValueError`。
- **引用计数没减到 $0$ 就放回空闲池**：其他序列还在用这个块。
- **`copy_on_write` 在 $\text{ref} = 1$ 时也分配了新块**：浪费，且测试会检查返回的是同一个编号。
- **用普通列表取最小值**：`min()` + `remove()` 是 $O(n)$，结果对但慢。

## 延伸

- **和操作系统的对应**：块分配器相当于操作系统的物理页帧管理器；每个序列自己的块表是页表；引用计数加写时复制，对应进程 `fork` 之后父子共享页面的做法。
- **块大小的取舍**：块越大，块表越短、一次读取的连续数据越多，kernel 更高效，但每个序列最后一块平均浪费得更多，也更难命中前缀缓存（只有满块才能共享）；块越小则相反。vLLM 的默认块大小是 $16$ 个 token，具体取值会随版本和后端变化。
- **一个块有多大**：一个块要装下 $P$ 个 token **所有层**的 K、V，字节数是 $P \times$ 每 token 的 KV 字节数（公式见「推理服务」专题）。分配器管理的是这个整体的编号，并不关心里面的内容。
- **容量规划**：启动时扣掉权重和激活的峰值，剩下的显存除以块的字节数，得到 `num_blocks`，之后不再动态申请显存，避免运行时的分配开销和碎片。
- **谁来拷贝数据**：`copy_on_write` 只管块编号和引用计数，数据拷贝由调用方负责：在 GPU 上把旧块的 K、V 复制到新块，再往新块写。
- **分配不到块时**：调度器要决定抢占谁（swap 或 recompute，见「推理服务」专题）。分配器自己只负责报错，策略不在这里。
- **并发**：真实引擎里分配器只在调度线程里调用，所以不需要锁；如果多线程使用，引用计数的修改必须是原子的。

## 面试追问

1. **为什么用块表代替为每个请求预留的连续空间？**
   请求的最终长度事先不知道，按最大长度预留会造成大量内部浪费，不同长度的段来去还会产生外部碎片。固定大小的块可以按需分配，没有外部碎片，每个序列最多浪费最后一块里没填满的部分。
2. **引用计数用来做什么？**
   让多个序列安全地共享同一个物理块：并行采样、束搜索的各个分支共享提示词的 KV。引用计数降到 $0$ 才说明没人用了，才能回到空闲池，提前回收会让其他序列读到被覆盖的数据。
3. **写时复制是怎么工作的？什么时候触发？**
   序列要往一个块里写新 token 时，如果这个块的引用计数大于 $1$，说明还有别人在读，不能原地改：分配一个新块，把数据拷过去，自己改用新块，旧块引用计数减 $1$。引用计数为 $1$ 时只有自己在用，直接写。
4. **为什么 `copy_on_write` 在没有空闲块时必须不改任何引用计数？**
   这是个先检查再修改的事务：如果先给旧块减了引用才发现没有新块可分配，状态就已经被破坏，调用方没法恢复。正确的顺序是先成功拿到新块，再改旧块的引用计数。
5. **碎片的上界是多少？**
   分页之后只有每个序列的最后一块可能没填满，浪费小于 $P$ 个 token，不依赖请求的最大长度。相比之下，按最大长度预留的浪费可以达到总预留量的绝大部分。
