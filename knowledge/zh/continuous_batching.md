## 背景

**静态批处理**：凑齐一批请求一起跑，整批中最长的那个结束后，才换下一批。问题很明显：

- 短请求早就生成完了，却要陪着长请求占着位置，GPU 上一部分算力在空转
- 新来的请求必须等当前整批结束才能开始，延迟很高

**连续批处理**（迭代级调度，Orca 提出，vLLM 采用）：调度的粒度从「一批」变成「一步」。每生成一个 token 就重新调度一次：结束的请求立刻离开，等待的请求立刻补进来。

## 核心概念

**两种步骤的代价不同**：

- **prefill**：新请求第一次运行，一次处理整个提示词（花费 `prompt_len` 个 token），并产生第一个输出 token
- **decode**：之后每步生成一个 token（花费 $1$ 个 token）

**每一步的预算约束**：

$$
\begin{aligned}
\underbrace{|\text{running}|}_{\text{decode 各 1}} + \sum_{r \in \text{本步新准入}} \text{prompt\_len}_r &\le \text{max\_batch\_tokens} \\
|\text{running}| + |\text{新准入}| &\le \text{max\_num\_seqs}
\end{aligned}
$$

**严格先来先服务（FCFS）**：按到达时间（再按编号）排队，队首放不下就停止准入，**不跳过**它去准入后面更小的请求。否则大请求可能永远排不上（饥饿）。

**完成时机**：请求在产生第 `output_len` 个 token 的那一步完成。那一步它仍在批次里（占槽位、占 token），从下一步起才释放。`output_len = 1` 的请求在被准入的那一步（prefill）就完成了。

**示例**：`[(0, 4, 2), (1, 2, 1)]`，预算 8 个 token、最多 2 个序列：

| 步 | decode | 新准入 | token 数 | 本步运行 | 结束 |
| --- | --- | --- | --- | --- | --- |
| 0 | — | 0（prefill 4） | 4 | `[0]` | — |
| 1 | 0（1） | 1（prefill 2） | 3 | `[0, 1]` | 0、1 |

## 用到的 Python 工具

- `sorted(range(n), key=lambda i: (arrival_i, i))`：FCFS 顺序。
- 一个列表记录每个请求还剩几个 token 要生成；`while any(left)` 驱动模拟。

## 常见坑

- **跳过放不下的请求**去准入后面的小请求：违反严格 FCFS。
- **结束的请求过早释放槽位**：它在完成的那一步仍计入 `max_num_seqs` 和 token 预算。
- **准入时忘了算上本步的 decode token**：预算是 decode 和 prefill 共享的。
- **跳过空闲步**：还没有请求到达时，要记录空列表 `[]`。
- **`prompt_len` 超过预算**：这样的请求永远无法调度，要提前抛 `ValueError`，否则会死循环。
- 每一步的请求编号要排好序。

## 延伸

- **为什么能做到迭代级调度**：Transformer 里除了注意力，其余各层（线性层、MLP、归一化）对每个 token 独立，把不同请求的 token 拼成一个大的 token 序列也没有问题；只有注意力需要区分序列边界。Orca 的「选择性批处理」（selective batching）就是这样做的：除注意力外的各层把所有请求的 token 拼在一起算，注意力则按请求分别算。
- **token 预算为什么重要**：每一步的耗时大致随处理的 token 数增长，`max_batch_tokens` 限制了单步的时长，也就限制了正在解码的请求遇到的最坏卡顿。`max_num_seqs` 限制并发序列数，防止 KV 缓存和调度开销失控。
- **显存也是准入条件**：真实调度器除了本题的两个约束，还要看是否有足够的空闲 KV 块。准入时要预估新请求需要多少块，不够就等，或抢占正在运行的请求（见「推理服务」专题）。
- **prefill 会拖慢 decode**：本题里一个长提示词的 prefill 会占掉大半个预算，同一步的 decode 请求要陪着这一步变慢。缓解办法是 chunked prefill：把提示词切块，每步只处理一部分，与 decode 请求共用预算；本题为简化起见不切块，所以要求 `prompt_len` 不超过预算。
- **FCFS 的取舍**：严格 FCFS 公平、不会饿死大请求，但队首放不下时会让后面的小请求也等着（队头阻塞）。真实系统可以做优先级、按预计长度排序等，换来更低的平均延迟，同时要小心饥饿。
- **和投机解码**：每个请求每步产生的 token 数可以大于 $1$（见「解码与采样」专题的投机解码），调度器需要按「每步实际处理的 token 数」而不是「请求数」来算预算。
- **输出长度未知**：本题的 `output_len` 是已知的，实际中请求什么时候结束要等模型生成结束符或到达长度上限，调度器只能边运行边发现。

## 面试追问

1. **连续批处理和静态批处理的区别是什么？**
   静态批处理按批调度，整批最长的请求结束后才换下一批：短请求结束后空占位置，新请求要等。连续批处理（迭代级调度）每生成一个 token 就重新调度一次，结束的请求立刻释放位置，等待的请求下一步就能加入。
2. **它为什么能提高吞吐，同时降低延迟？**
   吞吐上，GPU 不再因短请求提前结束而空转，batch 始终接近满的；延迟上，新请求不用等整批结束，排队时间大幅缩短。
3. **一个请求在调度里经历了什么？**
   先排队等待；被准入的那一步做 prefill（处理整个提示词，产生第一个输出 token）；之后每步 decode 一个 token；产生最后一个 token（或结束符）后离开，释放槽位和 KV 块。
4. **为什么要严格 FCFS，不让小请求插队？**
   如果队首的大请求放不下就跳过它，只要不断有小请求到来，大请求就可能永远等不到空位（饥饿）。严格 FCFS 保证先到先得，代价是队首放不下时后面的也得等。
5. **prefill 和 decode 混在同一批会有什么问题？怎么处理？**
   prefill 一步处理很多 token，同批的 decode 请求会被拖慢，用户看到的是生成中途的卡顿。可以用 token 预算限制每步总量，进一步用 chunked prefill 把长提示词切块、与 decode 共用预算，或者用 PD 分离把两个阶段放到不同的实例。
6. **怎么评估一个调度策略？**
   看 TTFT、TPOT（及其尾部分位数）和吞吐。调度策略总是在这几个指标之间折中：batch 大了吞吐高，但每一步慢、TPOT 变大；优先 prefill 让 TTFT 低，但会拖慢正在生成的请求。
