## 背景

语言模型逐个生成 token。生成第 $t$ 个 token 时，新 token 的查询 $q_t$ 要和**所有**历史 token 的 $k_1, \dots, k_t$、$v_1, \dots, v_t$ 做注意力。而历史 token 的 K、V 在之前的步骤里已经算过，并且不会改变（因果掩码保证前面的 token 看不到后面的）。

**KV 缓存**把算过的 K、V 存下来，每一步只为新 token 计算投影，然后拼到缓存后面。生成分两个阶段：

- **预填充**（prefill）：一次性处理整个提示词，$S_{\text{new}} > 1$，填满初始缓存
- **解码**（decode）：每步只输入 $1$ 个新 token，$S_{\text{new}} = 1$

## 核心公式

缓存里已有 $S_{\text{past}}$ 个位置，本次输入 $S_{\text{new}}$ 个：

$$
K_{\text{all}} = \bigl[\,K_{\text{cache}} ;\ K_{\text{new}}\,\bigr],
\qquad
V_{\text{all}} = \bigl[\,V_{\text{cache}} ;\ V_{\text{new}}\,\bigr]
$$

（$[\,\cdot\, ;\, \cdot\,]$ 表示沿序列维拼接），共 $S_{\text{total}} = S_{\text{past}} + S_{\text{new}}$ 个位置，然后

$$
\text{out} = \operatorname{softmax}\!\left(\frac{Q_{\text{new}} K_{\text{all}}^{\top}}{\sqrt{d_k}} + M\right) V_{\text{all}}
$$

**带偏移的因果掩码**：本次第 $i$ 个查询（$i = 0, \dots, S_{\text{new}} - 1$）在整个序列中的位置是 $S_{\text{past}} + i$，它能看到的键 $j$ 满足

$$
j \le S_{\text{past}} + i
$$

需要屏蔽的是 $j > S_{\text{past}} + i$，即形状为 $S_{\text{new}} \times S_{\text{total}}$ 的矩阵中，主对角线向右偏移 $S_{\text{past}} + 1$ 之后的上三角部分。解码时 $S_{\text{new}} = 1$，唯一的查询就是最新位置，所有键都可见，不需要掩码。

**省了多少计算**：不用缓存时，第 $t$ 步要重新投影全部 $t$ 个 token，生成 $T$ 个 token 共需 $\sum_{t=1}^{T} t = O(T^2)$ 次投影；使用缓存只需 $O(T)$ 次。

## 形状

| 量 | 形状 |
| --- | --- |
| `x` | `(B, S_new, d_model)` |
| 新的 $Q$、$K$、$V$（拆头后） | `(B, H, S_new, d_k)` |
| 缓存及拼接后的 $K$、$V$ | `(B, H, S_total, d_k)` |
| 分数、掩码 | `(B, H, S_new, S_total)`、`(S_new, S_total)` |
| 输出 | `(B, S_new, d_model)` |

## 用到的 PyTorch 操作

- `torch.cat([cache_k, k], dim=2)`：沿序列维拼接（拆头后的形状里序列在第 2 维）。
- `torch.triu(ones(S_new, S_total), diagonal=S_past + 1)`：`diagonal` 控制上三角从哪条对角线开始。
- 拆头 / 合头同多头注意力。

## 常见坑

- **拼接维度错**：`(B, H, S, d_k)` 的序列维是 `dim=2`，不是 `dim=1`。
- **掩码没有偏移**：直接用 `diagonal=1` 的方阵只适用于没有缓存的情况；有缓存时，新查询还要能看到全部历史位置。
- **返回的缓存不完整**：返回的应该是拼接**之后**的 K、V，下一步才能继续用。
- **缓存了投影前的输入**：缓存的是投影并拆头之后的 K、V，否则每步还得重新投影。
- 测试会检查：先预填充再逐个解码，结果必须和一次性完整前向完全一致。

## 延伸

- **缓存有多大**：每个 token、每层存一份 K 和一份 V，总量为 $2 \cdot L \cdot H_{kv} \cdot d_h \cdot b$ 字节每 token（$L$ 层数，$b$ 每元素字节数），与上下文长度和并发请求数成正比。这题的实现是 MHA，$H_{kv} = H$；GQA、MLA 压缩缓存的方式见「注意力」专题。
- **两个阶段的瓶颈不同**：预填充一次处理很多 token，是大矩阵乘，偏计算受限；解码每步一个 token，计算很少，却要读全部权重和整份缓存，偏访存受限（见「性能估算」专题的推理 roofline）。缓存把解码的计算从 $O(T^2)$ 降到 $O(T)$，但并没有消除它对带宽的依赖。
- **拼接的代价**：`torch.cat` 每步都会分配新张量并拷贝整份缓存，长序列下拷贝量不可忽略。实际引擎会预分配缓冲区原地写入，或者像「KV Cache 块分配器」「分页注意力」两题那样分块管理。
- **用旋转位置编码时存的是旋转后的 K**：K 的旋转只取决于它自己的位置，写入之后不会再变，所以可以直接缓存旋转后的结果；每步只需对新 token 的 Q、K 按其绝对位置旋转（见「位置编码」专题）。
- **batch 内长度不同**：一个 batch 里的请求缓存长度各不相同，简单做法是 padding 再用掩码屏蔽；更高效的做法是不补齐，直接按各自的长度处理（见「变长序列打包注意力」一题）。
- **解码 kernel**：只有一个查询时，并行度只靠 batch 和头数，序列又很长的话 GPU 吃不满，Flash-Decoding 沿 KV 长度再切一刀（见「IO 感知 kernel」专题）。

## 面试追问

1. **为什么只缓存 K、V，不缓存 Q？**
   第 $t$ 步的输出只需要当前这个 token 的 $q_t$ 与所有历史 K、V；历史 token 的 Q 之后再也不会被用到。K、V 则会被之后每一步重复使用，所以值得缓存。
2. **KV cache 占多少显存？举个例子。**
   $2 L H_{kv} d_h b$ 字节每 token。例如 $32$ 层、$8$ 个 KV 头、头维度 $128$、bf16，每 token 是 $2 \times 32 \times 8 \times 128 \times 2 = 131072$ 字节，即 $128$ KiB；$4096$ 个 token 约 $512$ MiB，每个请求一份。
3. **预填充和解码各自的瓶颈是什么？**
   预填充是大批量矩阵乘，偏计算受限，决定首 token 延迟（TTFT）；解码每步只算一个 token，要读全部权重和整份缓存，偏访存受限，决定每个 token 的间隔（TPOT）。
4. **有缓存时，因果掩码为什么要加偏移？**
   新的 $S_{\text{new}}$ 个查询在整个序列中的位置是 $S_{\text{past}}, \dots, S_{\text{past}} + S_{\text{new}} - 1$，每个都应当能看到全部历史和之前的新 token。掩码形状是 $S_{\text{new}} \times S_{\text{total}}$，上三角从偏移 $S_{\text{past}} + 1$ 的对角线开始。解码时 $S_{\text{new}} = 1$，不需要掩码。
5. **KV cache 的缺点是什么？**
   用显存换计算：缓存随上下文线性增长，长上下文、高并发时容易成为显存和带宽的瓶颈。后续的工作基本都围绕它展开：减少缓存的量（GQA、MLA、量化、滑动窗口）和管好缓存的存放（分页、前缀共享）。
6. **用了 KV cache，生成结果会变吗？**
   数学上完全等价，因为因果注意力下历史 token 的 K、V 本来就不依赖后面的 token。浮点上由于计算顺序和 kernel 不同，可能有极小的数值差异，这也是本题的测试用容差而不是逐位相等来比较的原因。
