## 背景

分页 KV 缓存把每个序列的 K、V 分散存放在不连续的物理页里（见「KV Cache 块分配器」一题）。注意力计算时就不能直接拿一段连续的张量，而要先通过**块表**（block table）找到这个序列的各页，再按顺序取出。这就是 vLLM 的 **PagedAttention**。

它和操作系统的虚拟内存一一对应：

| 操作系统 | PagedAttention |
| --- | --- |
| 虚拟页 | 逻辑块（序列中的第几块） |
| 物理页帧 | 物理页（KV 缓存池中的第几页） |
| 页表 | 块表 |
| 页内偏移 | 块内第几个 token |

## 核心公式

**地址转换**：每页存 $P$ 个 token（`block_size`），序列中第 $t$ 个 token 位于

$$
\text{物理页} = \text{block\_table}\bigl[\lfloor t / P \rfloor\bigr],
\qquad
\text{页内偏移} = t \bmod P
$$

**取出 K/V**：按块表顺序把各页取出、首尾相接，得到一段连续的 $K$、$V$，再截取前 $n$ 个（$n$ = `context_len`）有效 token。

**注意力**（单步解码，每个序列一个查询）：

$$
o = \operatorname{softmax}\!\left(\frac{q\, K_{1:n}^{\top}}{\sqrt{D}}\right) V_{1:n}
$$

**浪费**：每个序列只有最后一页可能没填满，浪费不超过 $P - 1$ 个 token 的空间。

## 形状

| 量 | 形状 |
| --- | --- |
| `Q` | `(B, 1, D)` |
| `k_pages`、`v_pages` | `(num_pages, P, D)` |
| `block_table` | `(B, max_blocks)` |
| `k_pages[block_table[b]]` | `(max_blocks, P, D)` |
| `reshape(-1, D)` 后 | `(max_blocks · P, D)` |
| 截取后 | `(n, D)` |
| 输出 | `(B, 1, D)` |

## 用到的 PyTorch 操作

- **用整数张量索引**：`k_pages[idx]`，`idx` 是一维整数张量，结果按 `idx` 的顺序取出各页。
- `t.reshape(-1, D)`：把 `(页数, P, D)` 展平成按 token 排列的 `(页数 · P, D)`，块内顺序保持不变。
- 切片 `[:context_len]`、`torch.softmax`、`@`。

## 常见坑

- **没有截取到 `context_len`**：最后一页未写满的位置是无效数据，参与 softmax 会污染结果。
- **展平维度错**：先 `(页, token, D)` → `(页·token, D)`，顺序是第 0 页的全部 token、再第 1 页……
- **所有序列共用一个块表行**：每个序列 $b$ 用自己的 `block_table[b]`。
- **缩放因子**：除以 $\sqrt{D}$。

## 延伸

- **这题是什么、不是什么**：题目用 gather 把各页拼成一段连续张量，再做普通的注意力，用来讲清楚「块表如何翻译地址」。真正的 PagedAttention kernel 不会先拷出一份连续的 K、V（那样会多读写一遍显存），而是在 kernel 里边查块表、边一块一块地读取，并用在线 softmax 的方式累积结果（见「IO 感知 kernel」专题）。
- **多层、多头**：真实系统里，一个物理页放的是一个块 $P$ 个 token、某一层的所有 KV 头；所有层用同一张块表，因为同一个序列各层的 token 位置相同。K 和 V 分别存在两个池里，使用同一个页号。
- **每个序列的长度不同**：本题 `context_len` 是标量，所有序列相同。实际引擎里每个序列有自己的长度，对应的 kernel 需要一个长度数组，块表也只填到各自需要的块数。
- **预填充怎么办**：分页对解码最关键。预填充时一次有很多个查询，K、V 往往是边算边写入块里，计算用的是刚算出来的连续张量或支持分页读取的 FlashAttention 类 kernel，具体做法因引擎而异。
- **代价**：多了一次间接寻址，访存不再是完全连续的。块越小，这个开销越明显；块大小通常取 $16$ 这样的值，一块的数据足够 GPU 做一次像样的合并读取。
- **共享**：因为只是改块表里的编号，多个序列的块表可以指向同一批物理页，从而实现前缀共享（见「前缀缓存」一题）。

## 面试追问

1. **PagedAttention 解决什么问题？**
   KV 缓存的显存管理。把每个序列的缓存切成固定大小的块，物理上不连续，用块表映射，消除了连续分配的预留浪费和外部碎片，让同样的显存能放下更多并发请求。
2. **块表怎么把 token 位置翻译成地址？**
   第 $t$ 个 token 在逻辑块 $\lfloor t / P \rfloor$，块内偏移 $t \bmod P$，物理页号是 `block_table[⌊t/P⌋]`。这和虚拟内存里「页号 + 页内偏移」的翻译是一回事。
3. **为什么要截取到 `context_len`？**
   最后一页通常没填满，后面的位置是旧数据或未初始化的内容。它们如果参与 softmax，会占走一部分概率，污染结果。
4. **分页会不会让注意力变慢？**
   会多一次查表，访存也不再是整段连续的，但只要块够大，每一块内部仍然是连续读取，开销很小。换来的是显存利用率提高、batch 更大，整体吞吐一般是上升的。
5. **分页与前缀共享、投机解码怎么配合？**
   共享只需要让不同序列的块表指向同一批物理页，写入时用写时复制隔离。投机解码（见「解码与采样」专题）验证失败时，需要丢弃一部分已写入的 token，对分页来说就是回退块内的写入位置，必要时释放多余的块。
